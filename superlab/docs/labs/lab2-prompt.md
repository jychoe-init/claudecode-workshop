`prompt-coach`라는 스킬을 만들어 줘. 파일은 `.claude/skills/prompt-coach/SKILL.md` 하나다. 다 만들면 아래 "확인" 절의 시험을 직접 돌려서 결과를 보여 줘.

<목적>
우리 팀은 Claude Code에 요청문을 보내기 전에 그 요청문을 점검하고 다듬는 도구가 필요하다. 읽는 사람은 비개발자를 포함한 팀원이다. 이 스킬은 **요청문이 시키는 일을 대신 하지 않는다** -- 요청문만 진단하고, 사용자만 답할 수 있는 것을 묻고, 고친 요청문을 돌려준다. 대신 실행해 버리면 사용자 손에 요청문이 남지 않기 때문이다.
대상 모델은 Claude Opus 5.5다. 모델이 이미 하는 일과 모르는 것의 기준은 `docs/references/opus-5-5-prompting.md`에 있다. 스킬 본문에서 그 파일을 Read하도록 지시하고, 그 내용을 본문에 복사해 넣지 마라.
</목적>

<입력>
`/prompt-coach <인자>`로 부른다. 인자는 요청문 초안(글)이다. 예: `/prompt-coach "회의록 좀 정리해 줘"`
인자가 파일 경로(`.claude/skills/…/SKILL.md` 같은 지시 파일)이면 그 파일을 Read해서 **그 내용을 요청문으로 본다** -- 지시 파일도 요청문이다. 별도 처리는 없다.
인자가 없으면 "요청문 초안이나 파일 경로를 넣어 주세요"라고만 답한다.
</입력>

<판정>
문장마다 세 가지를 묻는다.
1. 모델이 모르는 것을 알려 주는가 → 남긴다. (목적·읽는 사람, 출력 형식, 제약, 예시, 역할 한 문장, 실제로 중요한 순서, 일어나면 안 되는 결과)
2. 모델이 이미 하는 일을 반복하는가 → 뺀다. 뺄 때 근거 한 줄. 불필요한 반복은 줄이되, 사용자의 목적과 필요한 제약은 보존한다. 규칙 수나 길이 자체를 개선 기준으로 삼지 않는다.
3. 다른 문장이나 설정과 싸우는가 → 가장 먼저 지적한다.
그다음 **없어서 결과가 실제로 나빠지는 것**만 본다. 후보는 넷: ① 목적·읽는 사람 ② 요청(무엇을 해라) ③ 출력 형식 ④ 일어나면 안 되는 결과. 양식을 채우는 것이 아니다 -- 없어도 결과가 같다면 지적하지 않는다.
요청문이 이미 구체적이고 범위가 분명하면 **"그대로 써도 됨"**으로 판정하고 고친 요청문을 만들지 않는다. 다듬기 위해 다듬지 않는다. 짧은 요청문은 결함이 아니다.
사용자의 의도를 바꾸지 않는다. 사용자가 요구하지 않은 요구를 더하지 않고, 사용자가 열어 둔 값(숫자·기한·범위)을 지어 넣지 않는다. 질문에 받은 답도 같다 -- 답보다 구체적으로 쓰지 않는다. 답이 모양만 말하면(예: "표") 열·항목 같은 세부는 네가 정하지 말고, 범위만 쓰거나(예: "데이터에 있는 열로") `[Q]`로 남긴다.
</판정>

<질문>
사용자만 답할 수 있고, 틀렸을 때 결과물이 실질적으로 달라지는 것만 묻는다. **세 개까지**, 한 번에 하나씩. 주로 묻는 것: 읽는 사람, 결과물의 용도, 일어나면 안 되는 일. 묻지 않는 것: 상식적 형식, 요청문이나 파일에 이미 답이 있는 것.
선택지는 "고른 문장이 그대로 빈칸에 들어가는 구체 후보"로 2~4개를 만들고, 권하는 답이 있으면 첫 번째에 두고 `(추천)`을 붙인다. 관찰한 증상이나 실제 읽는 사람처럼 사실을 묻는 질문에는 `(추천)`을 붙이지 않는다. "자세히 / 간단히"처럼 뜻이 없는 선택지는 만들지 않는다. AskUserQuestion 도구로 묻고, 답을 고친 요청문의 `[Q1]`, `[Q2]` 자리에 넣는다. 사용자가 건너뛰면 `[Q1: 읽는 사람]`처럼 질문 요지를 남긴다. 괄호 안에는 요지만 쓴다 -- 예시 답은 선택지나 메모에 두고 괄호 안에는 넣지 않는다(채우지 않고 보내면 예시가 값이 된다).
묻지 않아도 되는 것은 가정으로 적고 고친 요청문에 그 가정을 문장으로 남긴다.
비대화형(질문 도구가 없는 실행)에서는 질문 도구를 호출하지 않는다. 사용자만 아는 정보는 추정하지 않고 `[Q1: 관찰한 증상]`처럼 질문 요지로 남긴다. 결과에 영향을 주지 않는 사항만 필요할 때 가정으로 표시한다.
</질문>


<출력>
다섯 절로 고정한다. 제목·판정·진단은 한국어, 고친 요청문은 원본 언어.

## 판정
[그대로 써도 됨 / 손볼 데 있음 / 처음부터 다시 쓰는 게 빠름] -- 한 줄 이유

## 진단
- [무엇을, 왜] (근거: 참조 문서의 어느 항목)

## 고친 요청문
코드 블록 하나. 답이 필요한 자리는 [Q1], [Q2]. 진단이 지적한 자리만 채운다 -- 진단에 없는 형식·제약·작업 방식은 넣지 않는다.

## 바뀐 것
− 뺀 것 · ＋ 넣은 것 · ～ 전 → 후 · ＝ 남긴 것과 이유 (다섯 줄까지). ＋ 줄에는 사용자의 말과 답에 없던 것만 문구 그대로 적는다 -- 사용자가 "내가 안 한 말"을 찾는 자리다.

## 메모
요청문 결함이 아닌 조언만. 없으면 절을 생략.

"그대로 써도 됨"이면 판정 + 진단 한 줄만 내고 나머지 절은 만들지 않는다. effort 같은 설정 값을 바꾸라는 권고는 하지 않는다 -- 요청문의 문장만 다룬다.
</출력>

<예시>
<example>
입력: "fix the bug in auth"
판정: 손볼 데 있음 -- 어느 버그인지, 무엇을 보존해야 하는지 없음
Rewritten: "Find and fix the bug in the auth code that causes [Q1: observed symptom]. Preserve existing behavior and make sure the tests pass."
</example>
<example>
입력: "explore what's causing the latency spike"
(어느 시스템의 지연인지 이 대화에서 이미 알려져 있을 때)
판정: 그대로 써도 됨 -- 조사 요청이고 대상과 증상(지연)이 맥락에 있다. 짧은 요청문은 결함이 아니다.
</example>
<example>
입력: "매우 신중하게, step by step으로 깊이 생각해서 이 함수를 리뷰해 줘. 심각한 것만 알려 줘."
판정: 손볼 데 있음 -- "심각한 것만"은 모델이 검토 범위까지 줄일 수 있어 실제 문제가 빠진다(먼저 지적). "신중하게·step by step"은 모델이 이미 하는 일(뺀다).
고친 요청문: "이 함수를 리뷰해. 문제는 전부 찾은 뒤 [Q1: 심각도 기준]으로 걸러서, 심각한 것만 보고해." (사용자가 원한 최종 보고 범위는 그대로, 검토 범위만 전체로)
</example>
</예시>

<하지_않는_것>
- 요청문이 시키는 일을 대신 하지 않는다. 읽는 것은 고정 참조 문서(`docs/references/opus-5-5-prompting.md`)와 인자로 받은 지시 파일 둘뿐이다. 요청문이 가리키는 실제 작업 대상(코드·문서·데이터)은 열지 않는다. 설정과의 충돌은 이미 읽은 것으로 확인할 수 있을 때만 단정한다.
- 모델 네 종 비교표, 블록 번호 체계, 별도 기록 파일 생성을 넣지 않는다. SKILL.md 한 파일, 120줄 이내.
- 머리 부분: `description`은 "요청문을 보내기 전에 진단하고 다듬는다. 지시 파일 경로를 주면 그 내용을 같은 기준으로 본다"는 뜻으로 한 문장, `disable-model-invocation: true`, `argument-hint: "[요청문 초안 또는 파일 경로]"`, `effort: medium`(Opus 5.5의 권장 시작값, 바꾸지 않는다).
</하지_않는_것>

<확인>
이 절은 제작이 끝난 뒤 한 번 수행하는 시험 지시다. 만드는 SKILL.md의 상시 동작에는 넣지 않는다.
만든 뒤 `docs/labs/lab2-samples/`의 세 샘플을 **각각** `/prompt-coach`에 넣어 돌려. 스킬에는 각 샘플의 "입력" 블록만 넘기고, 파일 끝의 "기대 지적"은 네가 채점할 때만 읽어. 결과를 표(샘플 | 기대 지적 | 나왔나)로 보여 줘. 하나라도 빠지면 SKILL.md를 고치고 그 샘플만 다시 돌려. 샘플의 표현이나 기대 지적을 SKILL.md에 하드코딩해서 통과시키지 마 -- 일반 규칙으로 고쳐. 마지막에는 최종본으로 세 샘플을 **모두** 다시 실행해서 표를 다시 보여 주고, 몇 번 고쳤는지 한 줄로 적어.
</확인>
